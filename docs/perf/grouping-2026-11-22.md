# 归组性能与日报引用成本：2026-11-22 测量结论

依据 `docs/plans/final-six.md` 项 3、项 4 的测量方案，对本机生产库只读执行。

## 归组性能（项 3）：无问题，不改造

| 指标 | 数值 | 结论 |
|---|---|---|
| 归组单次耗时 P50 / P95 / max | 0–3 s / 4.3–9.0 s / 26.5 s | 低于 10 s 决策线（P95 最高的 11-19 当天 worker 半日停摆，非常态） |
| 队列积压 | `events.group` 无 created/retry，全部 completed | 无积压 |
| 真实待归组 | 0 篇 | 库里 1990 篇 `grouping_status='pending'` 全是 block(1791)/unknown(197)，本就不归组 |
| 召回池规模 | 100–750 行/天 | 远未到需要粗召回/ANN 的量级 |
| 模型延迟 | `group_article` P95 ≈ 5.8 s/次，`group_review` 7.4 s | **模型段占绝对主导** |

按方案 3.6 的决策规则：模型延迟主导 → 若将来 P95 越线，先减候选数（召回 top/门槛），**不加并发、不做粗召回/pgvector**。bench 回放脚本不写。

**SQL 口径修正**：方案里"待归组"的 SQL ④ 应加 `JOIN sources ... participation_mode='editorial'` 且最新分析 `relevance='pass'` 过滤，否则 block/unknown 的存量会把数字放大两个数量级。

另：付费延迟分解的 `purpose` 取值共 7 个（`group_article/group_review/group_signal/group_card/group_card_review/group_story/group_story_review`），方案原文漏了后两个。

## 日报引用规范化（项 4）：砍掉

当前 **3 期**日报、合计 27 KB、平均 9 KB/期。远低于决策线（期数 < 200 或 p95 < 20 ms 即不做）。`firstDaily` 的 `jsonb_path_exists` 全表扫在这个规模下是微秒级。等期数过两百再按方案 4.3 重估。
